# Отчёт по Grafana для DormitoryHelper

## Цель и схема

Grafana запущена в Minikube в namespace `monitoring`. Источником временных рядов служит VictoriaMetrics Single из ДЗ-4. vmagent через Kubernetes service discovery собирает метрики backend, внешнего пробера и `postgres_exporter`.
Datasource provisioned как Prometheus-compatible источник с именем
`VictoriaMetrics`, потому что VictoriaMetrics поддерживает Prometheus HTTP API
и MetricsQL обратно совместим с используемыми PromQL-запросами.

## Dashboard приложения

В верхнем ряду собраны сигналы, позволяющие за несколько секунд оценить
состояние сервиса:

| Панель | Метрика / запрос | Причина выбора |
|---|---|---|
| Состояние приложения | `min(dormitory_helper_probe_success)` | внешняя проверка всей цепочки backend → PostgreSQL |
| RPS | `sum(rate(http_requests_total[5m]))` | RED Rate и Golden Signals Traffic |
| Ошибки 5xx | доля `http_requests_total{status=~"5.."}` | RED Errors; 4xx не считаются отказом сервиса |
| Latency p95 | `histogram_quantile` по `http_request_duration_seconds_bucket` | RED Duration и пользовательский хвост latency |
| SLA пробера | `100 * avg_over_time(dormitory_helper_probe_success[30d])` | договорная доступность из ДЗ-5, цель 98.5% |
| SLA error budget | нормализованный запас относительно 98.5% | показывает, можно ли расходовать бюджет отказов |

Для детализации используются RPS по HTTP-статусам и маршрутам, а также p50,
p95 и p99 latency. Это позволяет отличить общий рост трафика от проблем одного
endpoint и увидеть как типичную задержку, так и медленный хвост. Число запросов
in-flight отражает насыщение сервиса.

Runtime-панели показывают CPU, RSS/VMS и сборки мусора Python. Они основаны на
USE: utilization процесса, приближение к saturation по памяти/in-flight и
runtime-события, способные объяснить рост latency. Бизнес-панель показывает
частоту регистраций, входов и операций с объявлениями — технически здоровый
сервис может при этом не выполнять пользовательскую функцию.

## SLA внешнего пробера

SLA вынесен в отдельную stat-панель. Пробер раз в 5 секунд вызывает
`/health/ready`, который выполняет `SELECT 1`, поэтому результат учитывает и
backend, и PostgreSQL. Формула соответствует ДЗ-5:

```promql
100 * avg_over_time(dormitory_helper_probe_success[30d])
```

## PostgreSQL Exporter

Импортирован community dashboard **PostgreSQL Database**, Grafana.com ID 9628, revision 8. Он получает данные из того же datasource `VictoriaMetrics` и использует метрики sidecar `postgres_exporter` версии 0.20.1: `pg_up`, число соединений, транзакции commit/rollback, чтение и cache hits, изменения строк, locks, размер базы и параметры PostgreSQL.
Таким образом видны не только доступность базы, но и нагрузка и возможные узкие места.
