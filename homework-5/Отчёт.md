# Отчёт по SLI, SLO и SLA приложения DormitoryHelper

## 1. Использованные метрики

| Метрика | Тип | Что измеряет |
|---|---|---|
| `http_requests_total{method,handler,status}` | Counter | число HTTP-запросов backend с разбиением по маршруту, методу и коду ответа |
| `http_request_duration_seconds_bucket{le,method,handler}` и соответствующий `_count` | Histogram | распределение времени обработки HTTP-запросов; bucket `le="0.5"` содержит запросы не дольше 500 мс |
| `dormitory_helper_user_logins_total{outcome}` | Counter | попытки входа с исходом `success` или `failure` |
| `dormitory_helper_probe_success{target}` | Gauge | результат последней внешней проверки всей цепочки HTTP backend → PostgreSQL: 1 — успешно, 0 — ошибка |
| `dormitory_helper_probe_duration_seconds{target}` | Gauge | длительность последней внешней проверки |

Первые три семейства уже были реализованы в предыдущей работе. Внешний пробер
добавлен в этой работе. Пробер раз в 5 секунд обращается к
`/health/ready`; этот endpoint выполняет `SELECT 1`, поэтому проверяет не только
процесс backend, но и его зависимость PostgreSQL.

## 3. SLI и формулы

### 3.1 Временная доступность, TBSLI

Хороший временной интервал — scrape, в котором внешняя проба успешна.

```text
SLI_time = good probe samples / all probe samples × 100%
```

MetricsQL для демонстрационного окна:

```promql
100 * avg_over_time(dormitory_helper_probe_success[5m])
```

### 3.2 Доступность запросов, RBSLI

Хорошим считается обслуженный HTTP-запрос без ответа класса 5xx. Ошибки 4xx не
считаются недоступностью сервиса: обычно это некорректный запрос или отсутствие
прав пользователя.

```text
SLI_requests = (all requests − 5xx requests) / all requests × 100%
```

```promql
100 * sum(rate(http_requests_total{status!~"5..",handler!="none"}[5m]))
  / sum(rate(http_requests_total{handler!="none"}[5m]))
```

### 3.3 Быстродействие запросов, RBSLI latency

Хороший запрос завершается не дольше 500 мс.

```text
SLI_latency = requests with duration ≤ 0.5 s / all requests × 100%
```

```promql
100 * sum(rate(http_request_duration_seconds_bucket{le="0.5",handler!="none"}[5m]))
  / sum(rate(http_request_duration_seconds_count{handler!="none"}[5m]))
```

### 3.4 Успешность входа, дополнительный бизнес-SLI

```text
SLI_login = successful logins / all login attempts × 100%
```

```promql
100 * sum(dormitory_helper_user_logins_total{outcome="success"}) / sum(dormitory_helper_user_logins_total)
```

## 4. SLO

Для каждого SLI задана цель на скользящем окне 30 дней:

| SLI | SLO | Error budget за 30 дней |
|---|---:|---:|
| временная доступность | не менее 99.0% | 1.0%, то есть до 7 ч 12 мин простоя |
| HTTP-запросы без 5xx | не менее 99.0% | 1.0% запросов могут завершиться 5xx |
| запросы не дольше 500 мс | не менее 95.0% | 5.0% запросов могут быть медленнее |
| успешные входы | не менее 95.0% | 5.0% попыток могут быть неуспешны |

Общая внутренняя цель сервиса считается выполненной, когда одновременно
выполнены первые три SLO. SLO строже SLA и оставляет команде запас на реакцию.

## 5. SLA

SLA формулируется так: «За расчётный период 30 дней DormitoryHelper доступен не менее
98.5% времени по данным внешнего пробера.

```text
SLA_availability = successful probe intervals / all eligible intervals × 100%
SLA is met, if SLA_availability ≥ 98.5%
```

98.5% соответствует не более чем 10 ч 48 мин учитываемого простоя за
30 дней. Метрика соблюдения SLA:

```promql
100 * avg_over_time(dormitory_helper_probe_success[30d])
```

Остаток error budget SLA:

```text
remaining budget = (actual availability − 98.5%) / (100% − 98.5%) × 100%
```
