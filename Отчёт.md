# Отчёт по заданию № 1

## Доменная область

**DormitoryHelper** — клиент-серверная доска объявлений для жильцов студенческого общежития. Пользователь регистрируется или входит в систему, просматривает объявления, фильтрует их по тематике и управляет собственными объявлениями. Интерфейс реализован как одностраничное веб-приложение, взаимодействующее с backend по HTTP/1.1 REST API.

## Стек реализации

### Backend

- Python 3.12;
- FastAPI и Uvicorn;
- SQLAlchemy ORM;
- PostgreSQL;
- Pydantic для проверки входных данных;
- PyJWT для access- и refresh-токенов;
- Passlib (`pbkdf2_sha256`) для хеширования паролей;
- Poetry для фиксации зависимостей.

### Frontend

- React 19;
- React Router;
- Axios;
- HTML и CSS;
- Nginx для раздачи production-сборки.

### Запуск

Приложение упаковано в Docker-образы и объединено файлом `docker-compose.yml`. Инструкция запуска приведена в `README.md`.

## Основные сущности

### Пользователь (`User`)

- `id` — идентификатор;
- `name` — имя;
- `email` — адрес электронной почты, используемый при входе;
- `password` — хеш пароля;
- `announcements` — объявления пользователя.

### Объявление (`Announcement`)

- `id` — идентификатор;
- `name` — заголовок;
- `link` — ссылка или контакт;
- `category` — категория (`transport`, `sale` или `hobby`);
- `date` — дата и время начала;
- `end_date` — дата и время окончания;
- `user_id` — автор объявления.

Между пользователем и объявлениями установлена связь «один ко многим». При удалении пользователя удаляются принадлежащие ему объявления.

## CRUD

CRUD полностью реализован для основной сущности `Announcement`:

| Операция | HTTP-метод и маршрут | Реализация в интерфейсе |
|---|---|---|
| Create | `POST /announcements/` | форма создания |
| Read | `GET /announcements/`, `GET /announcements/{id}` | список и загрузка данных объявления |
| Update | `PUT /announcements/{id}` | форма редактирования |
| Delete | `DELETE /announcements/{id}` | кнопка удаления |

Изменять и удалять объявление может только его автор. API также предоставляет регистрацию, вход, обновление access-токена и получение профиля текущего пользователя.

## Соответствие методологии Twelve-Factor App

### I. Кодовая база (Codebase)

Backend, frontend, Docker-файлы и конфигурация совместного запуска находятся в одном Git-репозитории. Из одной кодовой базы можно создавать одинаковые образы для разных развёртываний; настройки окружений в код не вносятся.

### II. Зависимости (Dependencies)

Зависимости объявлены явно и изолированы. Backend использует `pyproject.toml` и `poetry.lock`, frontend — `package.json` и `package-lock.json`.

### III. Конфигурация (Config)

Параметры, различающиеся между окружениями, передаются через переменные среды: параметры PostgreSQL, размеры пула соединений, JWT-секрет, алгоритм подписи, разрешённые CORS-источники и внешние порты. Пример перечислен в `.env.example`. Production frontend использует относительный путь `/api`, поэтому его образ не привязан к адресу окружения. Значения по умолчанию предназначены только для локального запуска.

### IV. Сторонние службы (Backing services)

PostgreSQL рассматривается как подключаемый ресурс. Backend получает адрес и учётные данные из окружения и может быть переключён на другой экземпляр PostgreSQL без изменения исходного кода.

### V. Сборка, релиз, выполнение (Build, release, run)

Сборка отделена от выполнения Docker-образами. Оба Dockerfile являются multi-stage: в runtime backend не попадает Poetry, а в runtime frontend — Node.js и исходники. Frontend компилируется в статические файлы, зависимости backend устанавливаются по lock-файлу. Релиз образуется сочетанием неизменяемых образов и конфигурации окружения. Во время выполнения Nginx раздаёт готовые файлы, а Uvicorn запускает готовое приложение; установка пакетов на старте не производится.

### VI. Процессы (Processes)

Backend не хранит пользовательские сессии в памяти и аутентифицирует каждый запрос по самодостаточному JWT. Его процессы stateless и могут быть перезапущены или размножены. Постоянные данные вынесены в PostgreSQL. Frontend является набором статических файлов.

### VII. Привязка портов (Port binding)

Backend самостоятельно экспортирует HTTP-сервис на порту `8000` через Uvicorn, frontend — на непривилегированном порту `8080` контейнера через Nginx. Docker Compose публикует их наружу; внешние порты настраиваются переменными `BACKEND_PORT` и `FRONTEND_PORT`.

### VIII. Параллелизм (Concurrency)

Web-часть разделена на независимые типы процессов `frontend` и `backend`. Stateless backend допускает горизонтальное масштабирование несколькими экземплярами за балансировщиком.

### IX. Утилизируемость (Disposability)

Контейнеры можно быстро запускать, останавливать и заменять. При завершении Uvicorn прекращает приём запросов, а сессия SQLAlchemy закрывается после каждого запроса.

### X. Сходство разработки и эксплуатации (Dev/prod parity)

Для проверки и сдачи используется тот же Compose-стек, что и для развёртывания: PostgreSQL, собранный backend и production-сборка frontend за Nginx.

### XI. Журналирование (Logs)

Uvicorn, Nginx и PostgreSQL пишут журналы в стандартные потоки контейнеров.Локально их можно читать командой `docker compose logs`.

### XII. Задачи администрирования (Admin processes)

Инициализация схемы отделена от web-процесса и выполняется одноразовым сервисом `db-init` из того же backend-образа и с той же конфигурацией.
