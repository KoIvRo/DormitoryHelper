# Отчёт по развёртыванию DormitoryHelper в Kubernetes

## Цель работы

Упаковать приложение **DormitoryHelper** в Docker и развернуть приложение в одно-нодовом кластере Kubernetes, запущенном в Minikube.

В ходе работы были развёрнуты:

- frontend на React и Nginx;
- backend на FastAPI и Uvicorn;
- база данных PostgreSQL;
- одноразовая задача инициализации схемы базы данных.

## Сборка Docker-образов

Для развёртывания были собраны образы:

```text
dormitory-helper-backend:v1
dormitory-helper-frontend:v1
```

Образы были загружены в хранилище Minikube.

## Использованные абстракции Kubernetes

### Deployment

`Deployment` использован для запуска frontend, backend и PostgreSQL. Он описывает желаемое количество реплик Pod и восстанавливает Pod при их удалении/замене/аварий.

Для frontend и backend использование Deployment также позволяет выполнять горизонтальное масштабирование командой `kubectl scale`.

### Pod

`Pod` — минимальная единица Kubernetes. Pod не создавались вручную: ими управляли Deployment и Job.

### Service

Для компонентов созданы три Service:

- `postgres` — внутренний Service для подключения backend и Job к PostgreSQL на порту `5432`;
- `backend` — внутренний Service для доступа frontend к REST API на порту `8000`;
- `frontend` — Service типа `NodePort`, публикующий UI за пределами кластера на порту `30080` узла.

Service даёт группе Pod стабильное DNS-имя и распределяет запросы между её репликами. Связь Service с Pod задана через `selector`, совпадающий с labels в шаблоне Pod.

### ConfigMap

`ConfigMap` `dormitory-helper-config` хранит несекретную конфигурацию: DNS-имя и порт PostgreSQL, имя базы и пользователя, алгоритм JWT, CORS origins и параметры пула соединений SQLAlchemy. Значения передаются в контейнеры через переменные окружения.

### Secret

`Secret` `dormitory-helper-secret` хранит чувствительные параметры: пароль PostgreSQL и ключ подписи JWT. Backend получает весь Secret через `envFrom`, а PostgreSQL — только нужное значение `POSTGRES_PASSWORD` через `secretKeyRef`.

### PersistentVolume и PersistentVolumeClaim

`PersistentVolume` `postgres-data-pv` выделяет `1 GiB` дискового пространства на узле Minikube. `PersistentVolumeClaim` `postgres-data` запрашивает том с режимом доступа `ReadWriteOnce`. Claim подключается к PostgreSQL Pod, а том монтируется в `/var/lib/postgresql/data`.

Благодаря этому данные PostgreSQL не зависят от жизненного цикла конкретного Pod. Для PV задана политика `Retain`, поэтому после удаления PVC том и его данные не удаляются автоматически.

### Job

`Job` `db-init` запускает из backend-образа одноразовую команду `python manage.py`. Команда идемпотентно создаёт отсутствующие таблицы перед запуском web-части backend.

## Взаимодействие сервисов

Пользователь открывает frontend через Service `frontend` типа NodePort. Внешний порт `30080` перенаправляется на порт `8080` Nginx в frontend Pod.

React-приложение отправляет API-запросы на относительный адрес `/api`. Nginx удаляет префикс `/api/` и проксирует запрос на `http://backend:8000`. Имя `backend` разрешается внутрикластерным DNS Kubernetes в ClusterIP Service backend. Этот Service передаёт запрос одной из доступных реплик backend на порт `8000`.

Backend создаёт соединение с PostgreSQL, используя переменную `POSTGRES_HOST=postgres`. DNS-имя `postgres` указывает на Service PostgreSQL, который передаёт TCP-соединение в PostgreSQL Pod на порт `5432`. Job `db-init` использует ту же ConfigMap, Secret и Service PostgreSQL.

Схема взаимодействия:

```text
Браузер
   |
   | HTTP, NodePort 30080
   v
Service frontend
   |
   | TCP 8080
   v
Frontend Pod (React + Nginx)
   |
   | HTTP /api -> backend:8000
   v
Service backend
   |
   | TCP 8000
   v
Backend Pod(s) (FastAPI)
   |
   | PostgreSQL protocol -> postgres:5432
   v
Service postgres
   |
   | TCP 5432
   v
PostgreSQL Pod
   |
   v
PVC postgres-data -> PV postgres-data-pv
```

## Порядок развёртывания

Ресурсы применялись в следующем порядке:

1. ConfigMap и Secret;
2. PV, PVC и Service PostgreSQL;
3. Deployment PostgreSQL;
4. Job инициализации базы данных;
5. Service и Deployment backend;
6. Service и Deployment frontend.

## Масштабирование

В ходе демонстрации backend был масштабирован командой `kubectl scale`. После изменения желаемого числа реплик Deployment создал новые Pod, а Service автоматически включил их в балансировку по labels.

## Проверка работы

После развёртывания командой `kubectl get pods` было проверено, что Pod frontend, backend и PostgreSQL находятся в состоянии `Running`, а Pod одноразового Job — в состоянии `Completed`.

Работоспособность приложения была проверена через UI, открытый командой `minikube service frontend`. В интерфейсе были выполнены регистрация и операции с объявлениями. Все компоненты приложения корректно взаимодействовали внутри кластера.
